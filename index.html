智能驾驶（整车）测试中的数据自动化处理：入门指南

本文从“一辆测试车跑完一趟路后，数据如何自动变成测试结论”的角度，白话说明智能驾驶整车测试的数据、工具、脚本和实现流程。

一句话先记住：智能驾驶测试里的自动化数据处理，不是简单写一个脚本读 Excel；它通常是一条数据流水线：采集 → 上传 → 解析 → 对时/校验 → 场景切片 → 算指标 → 自动判定 → 出报告 → 回归对比。

一、智能驾驶整车测试，到底在测什么？

以搭载辅助驾驶/自动驾驶功能的整车为例，测试对象不只是“车能不能开”，而是整套闭环：

外界道路环境
   ↓
传感器感知
   ↓
算法识别、融合、定位、预测
   ↓
规划决策
   ↓
车辆控制（转向、制动、加速）
   ↓
车辆实际运动

例如测试“前车突然减速时，车辆能否自动刹车”，实际会关心：

  1. 摄像头、雷达是否看到了前车；
  2. 感知算法是否正确识别前车；
  3. 算法是否判断出碰撞风险；
  4. 规划模块是否决定制动；
  5. 控制模块是否及时下发制动请求；
  6. 制动系统是否真正建立制动力；
  7. 车辆是否避免碰撞；
  8. 整个过程是否平顺、舒适、没有误刹。

因此，整车智能驾驶测试数据会非常多，而且来自不同设备。

二、测试车通常采集哪些数据？

可以把测试车理解成一个“移动数据中心”。一次道路测试，常见会收集下面几大类数据。

1. 环境传感器数据

这是车“看见外界”的原始数据。

数据来源主要内容常见用途
摄像头前视、环视、侧视、后视视频或图片车道线、车辆、行人、交通灯、障碍物识别
毫米波雷达目标距离、速度、角度、雷达点迹/目标列表前车跟踪、雨雾等复杂环境下的探测
激光雷达三维点云三维障碍物、空间结构、定位、障碍物距离
超声波雷达近距离障碍物数据泊车、低速防碰撞
GNSS/RTK高精定位信息车辆真实位置、速度、轨迹评估
IMU加速度、角速度、姿态定位融合、急加速/急刹/转向分析

其中：

  • GNSS 是卫星定位；
  • RTK 是比普通 GPS 精度更高的定位方式，常可做到厘米级；
  • IMU 可以理解成测量车辆“怎么动”的惯性器件。

2. 车端总线和控制数据

这部分主要反映：车想干什么、车实际做了什么。

数据类型举例
CAN / CAN FD车速、方向盘角度、制动压力、档位、车门状态、转向灯状态
以太网数据摄像头、域控制器、高带宽传感器和算法模块通信
FlexRay / LIN部分车型中的底盘或低速控制通信
ECU / 域控制器日志软件错误、异常、运行状态、算法调试信息
控制指令目标加速度、目标转角、制动请求、换道请求
执行反馈实际转角、实际加速度、制动压力、横摆角速度等

例如，自动紧急制动（AEB）测试中，常常要对比：

算法请求制动的时刻
        ↓
控制器下发制动的时刻
        ↓
制动压力实际建立的时刻
        ↓
车辆速度真正下降的时刻

这几条曲线之间的时间差，就是重要测试指标。

3. 算法中间结果

原始视频和 CAN 信号只是“输入”和“车辆反馈”。智能驾驶测试还要看算法内部做出了什么判断。

模块常见输出
感知目标类别、目标位置、速度、置信度、车道线、红绿灯状态
融合多传感器融合目标、跟踪 ID
定位车辆坐标、姿态、定位置信度
预测周围车辆/行人的未来轨迹
规划本车未来轨迹、目标车道、期望速度、决策状态
控制期望方向盘角度、目标加速度、制动/加速指令
功能状态机ACC 是否激活、AEB 是否触发、LCC 是否可用、NOA 是否在执行变道等
只看“最后撞没撞”不够。一旦测试失败，需要根据这些中间数据判断问题发生在感知、决策、控制，还是车辆执行层。

4. 地图、道路与真值数据

为了判断算法“到底对不对”，还需要一个比较可信的参考答案，行业里常叫 Ground Truth（真值）。

  • 高精地图中的车道线、道路拓扑、限速信息；
  • RTK/组合导航得到的高精本车轨迹；
  • 目标车上安装的高精定位设备；
  • 人工标注出的车辆、行人、车道线；
  • 专业目标测量系统输出的相对距离和相对速度。
算法认为：前车距离 20.2 米，速度 40 km/h
真值系统测得：前车距离 19.8 米，速度 41 km/h

距离误差 = 0.4 米
速度误差 = 1 km/h

然后就可根据门限判断功能是否达标。

三、这些数据一般长什么样？

类型常见格式说明
视频.mp4、.avi、.h264、.h265摄像头录制内容
图片.jpg、.png单帧图像、截图、标注图
点云.pcd、.bin、.las激光雷达三维点云
车载总线日志.asc、.blf、.mf4、.dbcCAN/CAN FD 信号及定义
网络报文.pcap、.pcapng以太网抓包
机器人/算法消息包.bag、.mcap常用于按时间记录多路消息
定位轨迹.csv、.json、.kml经纬度、姿态、速度等

测试配置.yaml、.json、.xml车型、版本、场景、阈值、测试配置
  • .dbc：CAN 报文“字典”，告诉工具每个字节/位代表什么物理信号；
  • .mf4：常见的测量数据格式，属于 MDF 4；
  • .bag：ROS 生态中常见的时序消息记录格式；
  • .mcap：较新的机器人数据记录格式，设计目标之一是更高效地承载多种消息数据。

四、自动化处理数据的完整流程

测试车采集数据
    ↓
数据落盘（车载 SSD / 工控机）
    ↓
回库或网络上传到服务器/云存储
    ↓
自动校验文件是否完整、版本是否匹配
    ↓
解析各种格式，统一时间轴和信号名称
    ↓
从海量数据中筛选、切分目标场景
    ↓
调用算法或读取算法输出，计算评价指标
    ↓
按照规则自动判定 Pass / Fail / Review
    ↓
生成图表、视频回放、测试报告和问题单
    ↓
新版本重复跑同一批数据，做回归对比

第 1 步：采集和落盘

车辆跑测试时，通常会由车载工控机或数据采集系统同时记录：

  • 多路摄像头视频；
  • 雷达和激光雷达数据；
  • CAN/CAN FD 信号；
  • 定位、IMU；
  • 域控制器/算法日志；
  • 当前软件版本、地图版本、车辆 VIN、测试任务信息。

一个很关键的问题是：时间同步。

摄像头在 10:00:01.100 拍到前车刹车
雷达在   10:00:01.120 探测到目标减速
算法在   10:00:01.180 做出制动决策
CAN 信号在10:00:01.250 显示制动压力上升

如果设备时间不准，就无法准确判断系统到底慢了多少。所以整车测试会非常重视：GNSS 授时、PTP（精密时间协议）、统一时钟源、时间戳精度与多传感器对时。

第 2 步：上传、登记与自动校验

一趟测试可能产生几十 GB，甚至数 TB 数据。通常不能靠人工一个个拷贝、命名和检查。

1. 检查视频、CAN、雷达、定位文件是否齐全
2. 检查文件是否损坏
3. 检查每个文件的时间范围是否连续
4. 检查该数据属于哪辆车、哪个版本、哪位测试人员
5. 写入数据库，生成一条“测试任务记录”
6. 上传到 NAS、对象存储或云端数据湖

常见元数据包括：

{
  "vehicle_id": "TEST-CAR-012",
  "software_version": "AD-2.6.1",
  "map_version": "HDMAP-2026.10",
  "test_date": "2026-10-15",
  "route": "城市快速路-A线",
  "weather": "小雨",
  "data_start_time": "2026-10-15T09:30:00",
  "data_end_time": "2026-10-15T10:45:00"
}

这类信息不是“附属品”，而是后续定位问题、筛选场景、比较版本的基础。

第 3 步：解析不同格式，统一成可分析的数据

原始数据格式五花八门，不能直接混在一起分析。自动化脚本的重要作用，就是把它们转成统一的分析结构，例如时间序列表：

时间戳车速目标距离目标相对速度AEB 状态制动请求制动压力
10:00:01.0006035.2-4.0未触发00
10:00:01.1006034.5-8.0未触发00
10:00:01.20059.833.6-12.0触发-3.00
10:00:01.35058.531.8-15.0触发-5.020

核心工作包括：

  • 解码：把 CAN 原始报文翻译成车速、制动压力等物理量；
  • 解析：读取日志、算法输出、定位文件；
  • 对时：把不同数据源放到同一条时间轴；
  • 重采样/插值：统一采样频率；
  • 坐标转换：统一车辆坐标、世界坐标、地图坐标；
  • 清洗：处理丢帧、异常值、缺失值和重复记录。

现实中通常不是“一个超大脚本”，而是一组小工具/服务组合成平台。最常见的是 Python，因为它处理数据快、库多、写起来相对容易。

日志查询和监控ELK、Grafana、Prometheus 等

在个人电脑上入门时，常见组合是：

      + Git

一个非常简化的 Python 思路

例如，测试 AEB 触发是否及时。你已经把数据解析成一个 CSV：

timestamp,ego_speed_kph,front_distance_m,relative_speed_kph,aeb_active,brake_pressure_bar
0.00,60,40.0,-10,0,0
0.10,60,38.5,-15,0,0
0.20,59.9,36.7,-20,1,0
0.35,58.8,33.0,-25,1,18

脚本的思路大致是：

import pandas as pd

data = pd.read_csv("aeb_case_001.csv")

# 找到系统第一次进入 AEB 激活状态的时刻
aeb_rows = data[data["aeb_active"] == 1]

if aeb_rows.empty:
    result = "FAIL：未触发 AEB"
else:
    trigger_time = aeb_rows.iloc[0]["timestamp"]
    trigger_distance = aeb_rows.iloc[0]["front_distance_m"]

    # 示例规则：距离小于 40 m 时，必须在 0.5 秒内触发
    if trigger_time <= 0.5 and trigger_distance > 0:
        result = "PASS"
    else:
        result = "FAIL：AEB 触发过晚"

print(result)

真实项目当然会复杂很多，还会考虑目标是否真的是同车道前车、前车是否确实减速、自车状态是否允许 AEB、弯道/坡道/遮挡/切入车辆、TTC、是否误触发、制动减速度、是否碰撞、驾驶员干预和数据有效性等。

本质：把“测试要求”翻译成可计算的条件，再让程序在数据里找证据。

六、什么叫“场景切片”？为什么它很重要？

一辆车跑 2 小时，可能录了几百万条 CAN 信号、几万帧视频、海量点云；但你真正关心的，可能只是十几秒的“前车突然切入”片段。

自动化会根据触发条件，把长数据切成一个个“场景片段”，这就叫场景挖掘、场景切片或 Scenario Mining。

当以下条件同时成立时，截取一个“切入场景”：

1. 相邻车道目标横向距离快速向本车道靠近；
2. 该目标横向速度超过一定阈值；
3. 目标随后进入本车道；
4. 本车 ACC 或车道居中功能处于激活状态；
5. 截取触发前 10 秒、触发后 15 秒数据。

输出可能是：

2026-10-15 路测数据：
- 检出“前车切入”场景：36 个
- 其中 ACC 正确减速：31 个
- 存在舒适性问题：3 个
- 需要人工复核：2 个
自动化最大的价值，是从 TB 级数据中快速找出有价值的几秒钟。

七、整车智能驾驶常自动算哪些指标？

1. AEB：自动紧急制动

  • 是否识别目标；
  • 是否触发 AEB；
  • 触发时刻、TTC（预计碰撞时间）；
  • 制动建立延迟、最大减速度；
  • 最终是否碰撞、碰撞时相对速度；
  • 是否误制动；
  • 制动过程是否过于突兀。

2. ACC：自适应巡航

  • 是否正确识别前车；
  • 跟车距离是否保持在设定范围；
  • 加减速是否平顺；
  • 前车切入/切出后能否正确响应；
  • 前车刹停后是否跟停、前车起步后是否正确跟随；
  • 是否出现不合理急刹、急加速或频繁丢失目标。

常见计算指标：车间时距、相对速度、跟车距离误差、加速度、加加速度（Jerk，反映突兀程度）。

3. LCC / LKA：车道居中或车道保持

  • 是否识别左右车道线；
  • 横向偏差是否在允许范围；
  • 弯道中是否仍能居中；
  • 车道线模糊、缺失时是否合理退出；
  • 是否压线、偏离车道；
  • 转向是否频繁来回修正。
横向偏差：车辆中心偏离车道中心多少米
航向角误差：车辆朝向与车道方向差多少度
横向加速度：转弯时是否过猛
方向盘角速度：转向动作是否突兀

4. 自动变道 / NOA

  • 变道条件是否满足；
  • 是否漏看后方来车；
  • 是否正确判断周围空隙；
  • 是否打转向灯；
  • 变道时间和轨迹是否合理、平顺；
  • 是否压线、中途放弃或在禁变道区域违规变道；
  • 退出匝道、汇入主路是否正确。

5. 泊车功能

  • 能否找到车位；
  • 车位线/车位类型识别是否正确；
  • 是否规划出可行轨迹；
  • 是否与障碍物保持安全距离；
  • 是否完成泊入，最终停车位置是否合格；
  • 是否发生剐蹭、碰撞或过度靠近。

八、自动判定不能完全代替人工

自动化特别适合判断：

  • 某信号有没有出现；
  • 信号是否超过阈值；
  • 是否在规定时间内响应；
  • 距离、速度、偏差、延迟是否合格；
  • 两个版本的指标有没有变差；
  • 是否出现碰撞、压线、超速等明确定义的问题。

但以下问题通常需要人工复核：

  • 视频中目标到底是不是“行人”；
  • 车辆减速虽符合阈值，但驾驶体验是否明显不自然；
  • 算法行为是否符合复杂交通规则或业务意图；
  • 道路施工、临时标志、交警手势等长尾场景；
  • 数据或真值是否可信。
自动筛选全部数据
   ↓
自动计算指标、标红风险片段
   ↓
测试工程师查看视频、轨迹和信号曲线
   ↓
确认问题
   ↓
提交缺陷、跟踪修复、回归验证
自动化不是让测试工程师“不看数据”，而是让工程师不用把时间浪费在大量正常数据上。

九、仿真测试、台架测试和实车路测的自动化有什么区别？

测试层级在哪里测主要目的
MIL模型在环验证控制/算法模型逻辑
SIL软件在环在电脑上运行真实或接近真实的软件
HIL硬件在环使用真实 ECU，通过仿真输入测试
VIL车辆在环部分真实车辆、部分虚拟环境
封闭场地实车测试试验场可控验证高风险场景
开放道路路测真实道路验证真实交通和复杂长尾场景

仿真测试的自动化

仿真中不需要真的跑车，可以批量生成大量场景：

场景参数：
- 自车速度：40 / 60 / 80 km/h
- 前车速度：0 / 20 / 40 km/h
- 初始距离：10 / 20 / 30 / 50 m
- 路面：干燥 / 湿滑
- 光照：白天 / 夜晚 / 逆光
- 天气：晴天 / 雨天 / 雾天

程序将参数排列组合，自动运行成千上万次，再统计：

总场景：10,000
通过：9,920
失败：45
需人工复核：35

常见公开/开源生态：

  • CARLA：开源自动驾驶仿真平台，提供 Python API，适合创建车辆、交通参与者、传感器和场景；
  • Apollo：开源自动驾驶软件栈，包含感知、规划、控制、仿真等相关能力；
  • OpenSCENARIO：描述驾驶场景、角色和行为的行业标准；
  • OpenDRIVE：描述道路网络和道路几何信息的行业标准；
  • MCAP：面向机器人等时序消息数据的记录格式和生态。
OpenDRIVE：这条路长什么样
OpenSCENARIO：谁在这条路上，什么时候做什么动作
仿真器：让这些车、人、道路、天气真正跑起来
自动化脚本：批量运行、计算结果、判定通过或失败

测试工程师日常可能是在平台上做这些事：

  1. 选择测试功能，例如 AEB 或 ACC；
  2. 选择软件版本、车辆、路线或数据集；
  3. 选择自动化测试用例；
  4. 点击执行；
  5. 等待平台批量跑脚本；
  6. 查看通过率、失败场景；
  7. 点开失败记录，看视频、轨迹、CAN 曲线；
  8. 创建 Bug；
  9. 新版本出来后，对同一批数据再次执行；
  10. 比较新旧版本结果。

十一、刚入门应该重点学习什么？

第一阶段：车辆和测试基础

  • ADAS、智能驾驶功能基本概念；
  • ACC、AEB、LKA/LCC、BSD、DOW、APA、NOA 等功能；
  • 车辆纵向控制与横向控制；
  • CAN、CAN FD、DBC 的基本概念；
  • 软件测试基础：测试用例、缺陷、回归、边界值、场景法。

你不必一开始就懂复杂算法，但一定要能回答：这个功能在什么条件下该触发？不该触发时为什么不能触发？功能正确与否应该看什么数据？

第二阶段：学习 Python 数据处理

Python 基础
→ CSV / JSON 文件读取
→ pandas 表格数据处理
→ NumPy 数值计算
→ Matplotlib / Plotly 画曲线
→ 异常处理、日志记录
→ 单元测试
→ Git

例如你要能用 Python 完成：

  • 读取 CAN 解码后的 CSV；
  • 按时间段筛选数据；
  • 求最大值、最小值、平均值；
  • 找到信号第一次触发的时间；
  • 计算两个事件的时间差；
  • 判断是否超过阈值；
  • 生成 Excel/HTML/PDF 报告；
  • 画出车速、制动压力、目标距离的时间曲线。

十二、一个最实用的入门练习

假设你要做一个“小型 ACC 测试数据分析器”。准备一份 CSV：

time_s,ego_speed_kph,lead_distance_m,relative_speed_kph,acc_active
0.0,60,45,-2,1
0.1,60,44.8,-2,1
0.2,59.8,44.4,-4,1
...

你的第一个自动化测试脚本可以验证：

  1. ACC 是否处于激活状态；
  2. 前车存在时，跟车距离是否低于安全阈值；
  3. 相对速度明显变小时，自车是否开始减速；
  4. 是否有明显急刹；
  5. 输出 PASS / FAIL；
  6. 画一张速度和距离随时间变化的图。

这已经是智能驾驶数据自动化的一个缩小版了。

最后总结

智能驾驶整车测试的自动化数据处理，本质上是在做三件事：

  1. 把不同设备产生的大量原始数据，变成统一、可信、可分析的数据；
  2. 把测试用例的自然语言要求，变成程序能计算的规则和指标；
  3. 自动从海量数据中找场景、给结论、定位问题，并支持新版本回归。

而你最值得优先掌握的能力是：

测试思维
+ 智能驾驶功能理解
+ CAN/车辆信号基础
+ Python 数据处理
+ 自动化脚本与报告能力
